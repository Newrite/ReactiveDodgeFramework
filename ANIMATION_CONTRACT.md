# RDF animation contract

What the behavior patch (`behavior/Pandora_Engine/mod/rdf`, generated by `tools/gen_rdf_patch.py`) expects from an animation
set, and what the C++ plugin must do to drive it. All names below are parameters at the top of `tools/gen_rdf_patch.py`.

## 1. Files

9 hkx files in `meshes\actors\character\animations\RDF\` (data-relative), registered in the animationNames of BOTH
`DefaultMale` and `DefaultFemale` (the patch does this; the graph refers to them as `Animations\RDF\<name>.hkx`). One
dodge per direction, no roll / step kinds (until 2026-10-23 there were 18: `rdf_roll_*` 0..7, `rdf_step_*` 8..15, two
neutral):

| `RDF_DodgeClip` | file | direction |
|---|---|---|
| 0 | `RDF_Dodge_Forward.hkx`       | forward       |
| 1 | `RDF_Dodge_ForwardRight.hkx`  | forward-right |
| 2 | `RDF_Dodge_Right.hkx`         | right         |
| 3 | `RDF_Dodge_BackwardRight.hkx` | back-right    |
| 4 | `RDF_Dodge_Backward.hkx`      | back          |
| 5 | `RDF_Dodge_BackwardLeft.hkx`  | back-left     |
| 6 | `RDF_Dodge_Left.hkx`          | left          |
| 7 | `RDF_Dodge_ForwardLeft.hkx`   | forward-left  |
| 8 | `RDF_Dodge_Neutral.hkx`       | neutral       |

Neutral: a fresh dodge pressed without move input that keeps facing (the default `bBackstepWithoutInput=1` makes it a
backstep). Its default content is a copy of the backward clip, so nothing changes until a set provides its own; its motion
is still the plugin's, so a neutral clip should move the way `bBackstepWithoutInput` sends it (back by default). A chain
without input keeps the running dodge's heading and uses the directional clip. First person: `DodgeBack`.

Direction order is clockwise from forward. Each clip is authored relative to the character's facing; the plugin picks the
clip that matches the dodge direction relative to the actor (a dodge that turns the actor to its path plays Forward).

Clips must be Skyrim SE 64-bit hkx on the vanilla human skeleton (`Character Assets\skeleton.hkx`), 30 fps.

Development placeholders: `tools/install_fixtures.py` copies 9 clips (its sidesteps) of the user's own "The Ultimate Dodge Mod" into
the RDF mod folder under these names. They are NOT redistributable (the author's work), are gitignored, and must be
replaced before anything is published.

## 2. Timing

- Length about 0.6 - 0.8 s each. The plugin always ends the dodge (`RDF_DodgeExit`) and scales playback so the clip
  spans its timeline; a clip that is longer simply holds its last frame until then. There is deliberately no clip-end
  exit: a clip played for the first time in a session is still streaming in and has zero length, so a trigger relative
  to its end fired on entry and dropped the dodge.
- Blends: in 0.12 s (`RDF_DodgeInBlend`), chain into the other state 0.10 s (`RDF_DodgeChainBlend`), out 0.25 s
  (`RDF_DodgeOutBlend`). Tune in `tools/gen_rdf_patch.py` (`FX_IN/FX_CHAIN/FX_OUT`), regenerate, re-run Pandora.
- Playback speed = variable `RDF_DodgeSpeed` (float, default 1.0), bound on every clip, so the plugin can scale the clip to
  the dodge duration it simulates (`speed = clipLength / dodgeDuration`).
- First and last frame should be a neutral standing pose; the out-blend returns to whatever `Default_State` was doing
  (weapon drawn / sheathed / magic) through the vanilla sync variable `currentDefaultState`.

## 3. Root motion

RDF ignores clip root motion by design. Direction and displacement belong to the plugin. The states bind `bAnimationDriven`
(bIsActive0) and `RDF_IsDodging` (bIsActive1) on a `BSIsActiveModifier`, exactly like vanilla's
`bAnimationDriven_IsActiveMod`. The patch ships no animation-data block (Pandora native patches cannot carry them), so the
engine has no motion table for these clips. Author clips in place, or with motion you do not rely on.
Not verified in game: whether a clip WITH root motion but without an animdata block moves the actor.

## 4. Graph interface (what the plugin sees)

Events (appended to 0_master; send with `NotifyAnimationGraph`):

| event | direction | meaning |
|---|---|---|
| `RDF_DodgeStart` | plugin -> graph | root wildcard: from ANY root state go to `RDF_Dodge_A` (0.12 s blend). Set `RDF_DodgeClip` and `RDF_DodgeSpeed` first. |
| `RDF_DodgeChain` | plugin -> graph | while dodging: A -> B or B -> A (0.10 s). Set `RDF_DodgeClip` first. Use it to dodge again from inside a dodge; `RDF_DodgeStart` while already in A does nothing (no self transition). |
| `RDF_DodgeExit` | plugin -> graph | leave to `Default_State` (cancel, buffered attack/block). |
| `RDF_DodgeEntered` | graph -> plugin | enter notify of A and B. |
| `RDF_DodgeLeft` | graph -> plugin | exit notify of A and B; also fires when stagger/ragdoll/death/swim wildcards pull the actor out. |

Variables (appended to 0_master):

| variable | type | default | use |
|---|---|---|---|
| `RDF_DodgeClip` | int | 0 | selects one of the 9 clips (8 directions + neutral); read when the state is entered |
| `RDF_DodgeSpeed` | float | 1.0 | clip playback speed multiplier |
| `RDF_IsDodging` | bool | false | bound to the state's BSIsActiveModifier; the plugin sets it true before `RDF_DodgeStart` and false after `RDF_DodgeLeft` |
| `RDF_ArmBlend` | float | 0.0 | arm stance layer weight: 0 = arms follow the dodge clip, 1 = arms hold the current weapon stance (iRightHandType / iLeftHandType), linear in between. Write it before the dodge starts ([Graph] fArmStance, default 1). See BEHAVIOR_INTEGRATION.md section 5 |
| `RDF_ChainIndex` | int | 0 | which dodge of a chain is playing: 0 the first, 1 the second, 2 the third, ... Written by the plugin before `RDF_DodgeStart` / `RDF_DodgeStartB` / `RDF_DodgeChain` (so a clip generator or a transition condition sees the new value when the state is entered), and set back to 0 when the dodge is over however it ended (clip end, cancel into an attack / block, stagger, graph left, rollback, camera switch, the actor's agent released, a loaded save). Read-only for the graph: use it to swap clips or branch on the second / third dodge |
| `RDF_AttackFromDodge` | int | 0 | the attack playing came out of a dodge: 1 attack, 2 power attack, 0 otherwise. Written by the plugin before that attack starts (one update after the graph left the dodge), back to 0 when the attack ends, when the next attack starts (a combo going on from it is made of ordinary attacks) or when a dodge starts. Meant for OAR conditions on attack clips, see "Dodge attacks" below |
| `RDF_AttackFromDodgeClip` | int | 0 | the `RDF_DodgeClip` of that dodge (0..7 F FR R BR B BL L FL, 8 neutral); valid while `RDF_AttackFromDodge` > 0 |
| `bAnimationDriven` | bool (vanilla, index 81) | - | bound to bIsActive0 |
| `DF_IsDodging` | - | - | TDM's variable. It does NOT exist in this modlist's 0_master, so it is neither created nor bound. If it ever exists, generate with `--with-df` and it is bound to bIsActive2. |

With a weapon drawn in third person the dodge plays inside `1hm_behavior` (`RDF_1H_Dodge_A/B`, started by
`RDF_DodgeStart1H` / `RDF_DodgeStartB1H`, BEHAVIOR_INTEGRATION.md 7); the clips, variables and annotations are the same.

Order for a dodge from C++: set `RDF_DodgeClip`, set `RDF_DodgeSpeed`, set `RDF_ArmBlend` (0 or 1), set `RDF_ChainIndex`, set `RDF_IsDodging` true, send `RDF_DodgeStart`.
Chained dodge: set clip/speed, send `RDF_DodgeChain`. End: wait for `RDF_DodgeLeft` (or send `RDF_DodgeExit`), set
`RDF_IsDodging` false.

Interrupts: the vanilla root wildcards `staggerStart`, `WardBreak`, `Ragdoll`, `JumpStandingStart`, `SwimStart`, `bleedOutStart`,
horse and kill-move wildcards apply from the RDF states (verified in the staged Pandora output). The player's `StaggerPlayer`
is NOT a wildcard in vanilla (each vanilla root state carries its own copy), so both RDF states have one ->
`PlayerStagger_State`. Death/ragdoll (`DeathAnim`, `Ragdoll`) come from the `Master_Behavior` wildcards.

## 5. Annotations (optional, recommended)

A clip may announce its own cancel windows with annotations on its first track (`NPC Root [Root]`). The names are
registered as events in `0_master` by the `rdf` Pandora patch, which is what lets the engine forward them to the plugin.
When a dodge's clip sends `RDF_Windows`, that dodge ignores the ini timers (`fChainFrom`, `fAttackFrom`, `fBlockFrom`,
`fExitFrom`, `fIFrameStart/End`) and opens each window when its annotation fires; a clip without them keeps the timers.

| Annotation | Meaning |
|---|---|
| `RDF_Windows` | at 0: this clip carries windows |
| `RDF_IFrameStart` / `RDF_IFrameEnd` | invulnerability window (when `bIFrames=1`) |
| `RDF_PerfectStart` / `RDF_PerfectEnd` | optional perfect-dodge window; a clip without them keeps `fPerfectWindowStart/End` even when its other windows are annotated |
| `RDF_ChainOpen` | a buffered dodge may chain from here |
| `RDF_AttackOpen` | a buffered attack may cancel the dodge from here |
| `RDF_BlockOpen` | a buffered block may cancel the dodge from here |
| `RDF_ExitOpen` | with move input held, hand over to running from here |
| `RDF_CastOnClip` | at 0: this clip places its own CastOn moments. CastOn rules that accept an annotation wait for it instead of their delay (or fire at the dodge's end if the clip never reaches it) |
| `RDF_CastOnDodge` / `RDF_CastOnDodge.<tag>` | the moment the CastOn rules of the Dodge trigger fire: untagged ones on the plain annotation, tagged ones on their tag (docs/CASTON_DESIGN.md) |
| `RDF_CastOnPerfectDodge` / `RDF_CastOnPerfectDodge.<tag>` | the same for PerfectDodge rules; reached before the perfect hit, they fire at the hit |
| `RDF_Motion.<distance>,<startup>,<active>,<recovery>` | at 0: how this clip moves. The distance it covers and its phases, in clip seconds at speed 1; they add up to the clip's length. They replace `[Motion] fDistance` and `[Timing] fStartup / fActive / fRecovery` for this dodge. `RDF_Motion.<distance>` alone changes the distance only. Taken while the dodge is still in its startup: the speed curve is planned again from the same carry-in speed, and the distance already covered is kept |
| `RDF_Speed.<multiplier>` | at 0: this clip's own `[Graph] fAnimSpeed` (0.1 .. 5): `RDF_DodgeSpeed` = it x the clip's length / the phases. The dodge's timeline stays; above 1 the clip finishes early and holds its last frame until the exit, below 1 it is cut by the exit blend |
| `RDF_ExitBlend.<run>,<block>,<attack>` (or one value for all three) | at 0: this clip's own `[Timing] fExitBlend` / `fActionExitBlend` / `fAttackExitBlend`: how long its momentum takes to run out when cancelled into running, a block or an attack (0.02 .. 1 s; the attack's may be 0). Until the dodge starts exiting |
| `RDF_ArmStance.<share>` | at 0: this clip's own `fArmStance` / `fArmStanceFirstPerson` (0 = the clip moves the arms, 1 = the weapon stance stays). Only where there is a stance to keep, as at the start (a drawn weapon, or `bArmStanceWhenSheathed`) |
| `RDF_Steer.<startup>,<active>,<recovery>[,<maxDeviation>]` | at 0: this clip's own `[Steering] fRateStartup / fRateActive / fRateRecovery` (deg/s, 0 .. 10000) and, if given, `fMaxDeviation` (deg, 0 .. 180). 0 everywhere = the clip keeps its start direction |
| `RDF_Warp.<degrees>` | at 0: this clip's own `[Steering] fOrientationWarpMax` (0 .. 90): how far the body turns past a directional clip toward the real path. A set that reuses one clip for two directions wants up to 45, a full 8-direction set 22.5 or 0 |
| `RDF_RunSpeed.<units per second>` | at 0: this clip's own `[Motion] fRunSpeed` (0 .. 1500): the speed a dodge with move input held hands over into running (its curve is planned again to end at it) |
| `RDF_YawRate.<face>[,<startup>]` | at 0: this clip's own `fFaceYawRate` and, if given, `fStartupYawRate` (deg/s): how fast the body follows the path |
| `RDF_Commit.<seconds>` | at 0: this clip's own `fDirectionCommitTime` (0 .. 0.5): how long the live input still re-aims the dodge outright |
| `RDF_JumpOpen` | the jump (`[Jump] bBlockDuringDodge`) may cut the dodge from here. Without it the exit window decides; it only opens the jump earlier, it cannot hold it shut past `RDF_ExitOpen` |
| `RDF_ClipLength.<seconds>` | at 0: the clip's real length, replacing `[Graph] fClipLength` / `fClipLengthFirstPerson`, so `RDF_DodgeSpeed` makes it span its own timeline. The clip's length cannot be read from the game: a clip played for the first time is still streaming in and reports 0 |

`RDF_Motion`, `RDF_ClipLength`, `RDF_Speed`, `RDF_ExitBlend`, `RDF_ArmStance`, `RDF_Steer`, `RDF_Warp`, `RDF_RunSpeed`,
`RDF_YawRate` and `RDF_Commit` carry their numbers
after the first '.': the graph splits an annotation there, and the rest arrives as the event's payload, so each name is
registered once. `[Graph] bClipMotion=0` ignores all of them (`RDF_JumpOpen` is a window and always counts). A
malformed or out-of-range one is ignored and logged with `bDevLog`. Limits: distance 0..5000, each phase 0..5 s with a
total of at least 0.05 s, length 0.05..10 s.

Times are clip-local; the plugin does not need to know the playback speed. Windows reset at every dodge, including a
chain, so the incoming clip announces its own.

`tools/annotate_clips.py` writes them reproducibly (serde-hkx: hkx -> xml -> hkx; replaces earlier `RDF_*` annotations,
keeps `animmotion`, PIE and others). It places them from the clip's root-motion speed curve, as the first key after the
speed peak where the speed has fallen to a fraction of the peak: attack and block at 90 % (right after the peak, and
never later than 0.35 s), chain and exit to running at 75 % (still moving, so the blend lands in running instead of a
planted stance); i-frames run from the first key at 30 % of peak until 60 % after the peak. Every fraction is a
command-line option (`--attack`, `--block`, `--chain`, `--exit`, `--iframeEnd`).
It also writes `RDF_Motion` and `RDF_ClipLength` unless `--no-motion` is given:
- the distance is the root motion's horizontal path length, times `--distanceScale`;
- the startup lasts until the speed first reaches 85 % of its peak;
- the active phase lasts until the speed falls below 85 % again;
- the recovery is the rest of the clip;
- the length is the clip's own duration.

These settings are not measured from the clip. When given, they are written with the same value for every clip of the
run:
- `--speed <x>` writes `RDF_Speed.<x>`;
- `--exitBlend`, `--armStance` and `--steer` write the matching annotation;
- `--jumpOpen <s>` writes `RDF_JumpOpen` at that time; `--jumpOpen exit` writes it at the clip's `RDF_ExitOpen`.

A set spec takes `"clipSettings"` and `"jumpOpen"` for the same.

`build_clip_set.py` does the same for every set; a spec takes `"motion": false`, `"distanceScale"` and `"speed"`.

`behavior/clip_windows.json` records the times written. `tools/clip_analyze.py` prints the per-frame speed and
pelvis/head height of a clip for hand tuning. Note: the XML round trip keeps 6 decimals, so animation floats can move by
up to 5e-7.

## 6. Adding another clip set

### Per weapon (or any condition) — an OAR set, no Pandora run

The graph always plays `Animations\RDF\RDF_Dodge_<Direction>.hkx`. A set is an Open Animation Replacer mod
whose submod mirrors those 9 paths under its conditions, so it can be added, removed or reordered without
regenerating behaviours:

1. Write a spec in `behavior/sets/<name>.json`: target MO2 mod name, OAR mod/submod names, priority, the OAR
   conditions, and one source clip per direction (`f fr r br b bl l fl`). Roll and step slots get the same clip.
2. Extract the source archive into a new folder under `_work/` and run
   `python tools/build_clip_set.py behavior/sets/<name>.json --src _work/<folder>`. It writes the mod, copies
   the clips, adds the `RDF_*` windows (keeping the clips' own annotations) and records the times in
   `behavior/sets/<name>.windows.json`.
3. Enable the mod in MO2. Its OAR priority decides between sets; MO2 order does not matter.

Example: `behavior/sets/greatsword-2hm.json` -> mod `AI - RDF Dodge Set - Greatsword` (greatsword in the right
hand, not a spear).

Example with several submods in one mod: `behavior/sets/infinity-dodge*.json` -> mod `AI - RDF Dodge Set - Infinity Dodge`
(Infinity Dodge, a DMCO pack: `Default` for everything at 9200000, `Greatsword` 9200005 and `Battleaxe and Warhammer`
9200006 with the weapon drawn, as in the original). Build each spec into the same mod; `--src` is the pack's own OAR
folder (`...\OpenAnimationReplacer\Infinity Dodge`), `--mods` the MO2 mods folder. A clip made for another dodge
framework carries its events: list their prefixes in the spec's `dropAnnotations` (for DMCO packs `PIE.` = DMCO's stamina
payload and `MCO_nextdodge`, `SpecialFrames_` = extra i-frames, `MCO_` = MCO_Recovery / MCO_InputBuffer, which RDF's
attack-cancel rules would read as an attack's recovery). `Soundplay.MCO_DodgeSound` is kept: it sounds only while
DMCO's `Dodge_MCO-DXP.esl` (which defines that sound descriptor) is active.

### Replacing the default set


1. Author 9 clips with the naming and index convention above (the neutral one may be a copy of the backward one).
2. Put them in a new folder (e.g. `Animations\RDF2\`) and change `ANIM_DIR` in `tools/gen_rdf_patch.py`, or enlarge `CLIPS`
   to several sets: the selector simply grows (`RDF_DodgeClip = set * 9 + index`); nothing else in the graph changes.
3. `python tools/gen_rdf_patch.py && python tools/install_fixtures.py`, re-run Pandora, then validate:
   `python tools/stage_pandora.py --label rdf --rdf behavior/Pandora_Engine/mod/rdf` and `python tools/validate_rdf.py`.
   (`validate_rdf.py` takes the clip list and expected node count from the generator, so it follows the change.)

## 7. Arm stance layer (what clip authors need to know)

With `RDF_ArmBlend` > 0 the arm bones (right: clavicle, upper arm, forearm, hand, fingers, weapon bone, pauldron, magic node, twist
bones; left: the same plus the shield bone) are replaced by the vanilla weapon-ready idle pose of the player's current weapon
types, looping, while the rest of the body plays the dodge clip. Consequences for authoring:
- a dodge clip meant for `RDF_ArmBlend = 1` (side steps, back steps) may leave the arms at a neutral pose; they are overridden;
- a clip meant for `RDF_ArmBlend = 0` must animate the arms itself (it keeps full control of them);
- root motion always comes from the dodge clip, never from the stance layer.
The stance clips are vanilla files (`H2H_Idle`, `1HM_Idle`, `DW1HM1HMIdle`, `2HM_Idle`, `2HW_Idle`, `Bow_IdleHeld`, `StaffRight_Idle`,
`Staff_Idle`, `MRh_Idle`, `MLh_Idle`, `Tor_1HMPose`, `DLC01\CrossBow_IdleHeld`); a clip set does not have to provide them.

## 8. First person

The same events/variables work in first person: send `RDF_DodgeStart`/`StartB`/`Chain`/`Exit` to the 1P graph; the 1P state plays the
current weapon-ready 1P idle (no dodge clips), sets `bAnimationDriven` while `RDF_IsDodging` is true, sends `RDF_DodgeEntered` /
`RDF_DodgeLeft`. `RDF_DodgeClip`, `RDF_DodgeSpeed`, `RDF_ArmBlend` exist in the 1P graph but are not used. The clip-set files in
section 1 are 3P only. See BEHAVIOR_INTEGRATION.md section 6.

## Perfect dodge events (plugin -> graphs)
| event | sent to | when |
|---|---|---|
| `RDF_PerfectDodge` | the player | a hit the i-frames dodged inside the perfect window, once per dodge |
| `RDF_PerfectDodged` | the attacker | the same moment (humanoid graphs; creature graphs do not know the event) |
Both are registered in the patch's event list, so behaviors, OAR conditions and other plugins' graph-event sinks can
react to them. Papyrus gets the SKSE mod event `RDF_PerfectDodge` (sender = attacker, numArg = dodge time).

## Attack clips: dodge-cancel windows

An attack clip (any melee attack the actor plays, not ours) may say when a dodge cancels it:

| annotation | meaning |
|---|---|
| `RDF_DodgeCancelOpen` | from here a dodge may cancel this attack |
| `RDF_DodgeCancelClose` | from here it may not |

Any number of windows per clip. Once a clip announced either one, its windows alone decide (the attack framework's
recovery, `MCO_DodgeOpen`-style window events and `sAttackStates` no longer count for it). Until the first one fires
the other rules apply, so put `RDF_DodgeCancelClose` at 0.0 to make the clip decide from its first frame. Examples:

- feint only: `Open 0.0`, `Close 0.15`;
- cancel anything after the swing, even without a recovery: `Close 0.0`, `Open 0.45`;
- no cancel at all in this clip: `Close 0.0`.

The windows start over with each attack (the vanilla attack state passing through Draw, or one of
`[AttackCancel] sAttackStartEvents`). The anytime keywords (`[AttackCancel] sAnyTimeKeyword`, `sAnyTimePowerKeyword`) still
override a closed window.

An annotation only becomes an event when its text is an event of the behavior file that plays the clip. The patch
registers both names in `1hm_behavior` (3rd and 1st person), where vanilla melee attacks and BFCO's attacks play.
Attack clips of other behavior files (MCO's own `MCO_Attack.hkx`, `MCO_PowerAttack.hkx`, ...) need the two names in
that file's event list; until then they fall back to the recovery rules (`MCO_IsInRecovery`).

## Dodge attacks (OAR)

A unique attack out of a dodge needs no behavior work: the attack the framework plays (vanilla, MCO, BFCO, any) is
replaced by Open Animation Replacer while `RDF_AttackFromDodge` says it came out of a dodge. In the OAR submod that
replaces the attack clip (for BFCO e.g. `BFCO_PowerAttackA.hkx`, for vanilla `1HM_AttackPowerForward.hkx`) add a
condition comparing the graph variable:

```json
{
    "condition": "CompareValues",
    "requiredVersion": "1.0.0.0",
    "Value A": { "graphVariable": "RDF_AttackFromDodge", "graphVariableType": "Int" },
    "Comparison": "==",
    "Value B": { "value": 2.0 }
}
```

(The shape of a shipped OAR config comparing an Int graph variable, Animated Poisons Redone's `APR_PoisonAnim`.)

(2 = power attack, 1 = attack.) Add `RDF_AttackFromDodgeClip` for per-direction variants (4 = backward, 2 = right,
8 = neutral...). Give the submod a higher priority than the ordinary replacer of the same
clip. OAR evaluates conditions when the clip starts; the plugin writes both variables before the attack starts and
clears them when it is over, so the next attack of a combo plays its normal clip.

## Stagger clips: the dodge's escape window

`[Stagger]` decides when a dodge may cut a stagger short (first rule that decides wins: `sNoEscapeKeyword` never,
`sAnyTimeKeyword` always, the stagger framework's recovery window, `fDodgeDelay` / an effect with `sDelayKeyword`). The
recovery window is a bool graph variable (`sRecoveryVariables`, default `MSL_IsStaggerRecovery`: Modern Stagger Lock, set
by its clips and by Rim Combat) or open / close events (`sRecoveryOpenEvents` / `sRecoveryCloseEvents`, default
`MSL_RecovWinOpen` / `MSL_RecovWinClose` and our own `RDF_StaggerEscapeOpen` / `RDF_StaggerEscapeClose`); a new stagger
(`sStaggerStartEvents`) closes it. A stagger clip annotated with `RDF_StaggerEscapeOpen` .. `RDF_StaggerEscapeClose`
opens the escape for that part of the clip, but an annotation reaches the plugin only when the behavior file that plays
the clip registers it as an event: the RDF patch does not add them to the stagger behaviors (MSL's own behavior file is
prebuilt), so a clip author who wants them registers them in that behavior. The dodge out of a stagger costs `[Cost]
fCost + fEscapeCost` plus the magnitudes of active effects with `sEscapeCostKeyword`.
